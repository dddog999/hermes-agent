# 编码行为准则

减少 LLM 系统性编码缺陷的行为约束。**偏向谨慎而非速度**，简单任务可灵活处理。

## 1. 先想后写

**不擅自假设。有困惑就问。亮出权衡。**

- 明确陈述你的假设，不确定就问
- 有多种理解方式时，都列出来，不要默默选一个
- 有更简单的方案就说出来，可以反驳用户
- 搞不清的地方停下来，指明哪里困惑，然后问

## 2. 简洁至上

**最小代码解决问题。不写推测性代码。**

- 不加超出需求的功能
- 一次性代码不做抽象
- 不要的"灵活性"和"可配置"不要加
- 不可能的场景不做错误处理
- 200 行能 50 行搞定的，重写

自检："资深工程师会说这过度设计了吗？" 会的话就简化。

## 3. 精准手术

**只改必须改的。只清理自己产生的烂摊子。**

编辑已有代码时：
- 不"顺便改进"旁边的代码、注释、格式
- 不修没坏的东西
- 匹配现有风格，即使你会写得不同
- 看到无关的死代码，提一嘴，别删

自己的改动产生孤立引用时：
- 清理**自己引入的**未使用 import/变量/函数
- 不删原有的死代码，除非用户要求

验证标准：每一行改动都能追溯到用户的需求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

把任务转化为可验证目标：
- "加验证" → "写无效输入的测试，然后让它通过"
- "修 bug" → "写能复现的测试，然后修复"
- "重构 X" → "重构前后确保测试通过"

多步任务，列出简要计划：
```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
```

强成功标准 = 能独立循环。弱标准("让它能跑") = 需要不断追问。
