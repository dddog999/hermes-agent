# SQLite 数据库不能放文件同步服务

## 一句话

**SQLite + WAL 模式 + 坚果云/Dropbox/任何文件同步服务 = 定时炸弹。**

## 为什么

### 文件关系

SQLite WAL 模式下的数据库是三件套：

```
mydb.db       ← 主数据库
mydb.db-wal   ← 写前日志（未合并的变更）
mydb.db-shm   ← 运行时共享内存（无持久数据）
```

`.db` 和 `.db-wal` 必须在**同一个瞬间保持一致**。

### 文件同步服务的三个缺陷

| 缺陷 | 具体表现 |
|------|---------|
| **非原子同步** | 不能保证 `.db` 和 `.db-wal` 同时到达另一台机器 |
| **顺序不可控** | 可能先传 WAL 再传 DB，或者反过来 |
| **并发写入冲突** | 两台机器同时写同一个 `.db` 文件 → 最后同步的覆盖前一个 |

### 崩溃场景

```
机器 A checkpoint → db 更新, wal 清空
机器 B 同时写入新消息 → wal 追加新内容
坚果云: 同步 db(A的版本) + wal(B的版本)
                              ↓
                      db ↔ wal 不一致
                              ↓
              SQLite: "database disk image is malformed"
                         或静默丢数据
```

## 什么能放坚果云

| 文件类型 | 安全？ | 原因 |
|---------|--------|------|
| `.md`、`.txt`、`.json` | ✅ 安全 | 文本文件，冲突可手动合并 |
| `.db`、`.db-wal`、`.db-shm` | ❌ 危险 | 二进制格式，冲突后无法恢复 |
| `.jsonl` | ⚠️ 谨慎 | 追加日志格式，冲突时可能丢部分行 |
| 写完不再变的文件 | ✅ 安全 | 只读数据没有冲突问题 |

## 正确做法

### 方案 A：各自本地存 SQLite，坚果云只同步导出文本

```
~/.hermes/state.db     ← 本地 SQLite，每台机器独立
坚果云: wiki/raw/      ← 只存导出的 Markdown 文本
```

### 方案 B：选一个机器做主写者

一台机器写 SQLite，其他机器只读。可以通过坚果云同步只读的 `.db` 文件（前提是写机器 checkpoint 完成后确保 `.db` 完整）。

### 方案 C：不用 SQLite，直接用文本文件

```
memories.db.json       ← JSON 文件，坚果云可安全同步
```

JSON 冲突时至少可以手动合并。
